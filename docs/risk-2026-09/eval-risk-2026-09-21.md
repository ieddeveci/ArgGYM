## 1. Ranked: what would mislead

### 1.1 The shipped taskset asks questions that do not state the rules the scorer enforces — **not an open issue**

`PROMPT_VERSION`'s own docstring (`freeze.py:36-40`) records what versions 6 and 7 did:
"versions 6 and 7 each state rules the scorer was already enforcing ... the 280 engine-scored
and `formalization` questions at 6, the remaining 200 at 7." All 480 questions moved across
those two versions. The shipped file is at 5.

Measured:

```
$ python3 -c "... 'Any word in your answer outside these lines scores the whole answer zero.' in r['question'] ..."
shipped rows containing the v7 sentence: 0 of 480

$ uv run python -c "... TaskDataset(t, 3, 'last_link_elitist').build_at(0) ..."
claim_chain True  perturbation True  status_query True
semantics_query True  defeat_diagnosis True  formalization False   (present on 5 of 6)
```

`formalization` is False because it gets its own wording from v6 (`1ad8a5a`), not the shared
sentence.

What that rule costs, from the commit that added it (`16611df`): "Appending the word
`therefore` to a shipped reference takes all 40 rows of each from 1.0000 to 0.0000, and the
same holds on all 480 rows of the taskset." `UnparseableAnswer` is turned into a zero
`ScoreResult` (`answers.py:82`), so the item lands in the mean, not in `scorer_refused`.

**Direction and size.** Every model down. Not uniformly: the penalty falls on models that
write a connective, a label, or a sentence of commentary inside the answer region, so the
gap between a terse model and a chatty one is inflated by a format rule the chatty one was
never told. You cannot bound it without generations, but a single token is the whole
difference between 1.0 and 0.0 on every row of five tasks.

This is the largest single risk in the repo right now and it has no issue number.

### 1.2 Per-model token caps spanning 8x — **PR #151, not an open issue**

`#151` ("fixes/models added for the eval phase", 51 files) adds sixteen model configs, each
capped at that model's own maximum output allowance rather than at what the task needs:

```
$ grep -n "^+.*max_tokens" <pr151 diff>

16384  qwen3-8b, deepseek-r1-distill-qwen-7b, ministral3-3b-reasoning
24576  qwen3-14b

65536  gemini-2.5-pro, gemini-3.5-flash-lite, gemini-3.6-flash, gemini-3.7-flash, gemini-3.8-flash
```

`evals/run.py:68-71` states the rule this breaks, in the repo's own words: "Temperature and
the token cap change what the model was asked as surely as the prompt does — on this box a
24576-token cap scored eight of twelve tasks at exactly 0.000 and a larger one did not — so
generations made under two caps must not pool." `refuse_a_changed_run` enforces that inside
one run directory and cannot see across models. `evals/report.py:labels` appends the cap to a
column header **only on a name collision** (`report.py:98-105`), so sixteen differently-capped
models sit in one table with nothing in the header saying so.

**Direction.** Monotone in the cap. The small models get one eighth the budget of the Gemini
column, and the report's per-task `mean` will read "small models cannot do argumentation" when
a large part of it is "small models were cut off". The August pilot is the precedent: 74-89%
of items lost to truncation for three of seven models (`docs/evaluation.md`).

`mean_untruncated` exists and is printed, which is the mitigation — but it silently changes
the denominator per model, and a comparison across columns of `mean_untruncated` is a
comparison of different item subsets, weighted toward whatever each model finished quickly.

### 1.3 #129 / #131 — the two Qwen configs on `main` ship the cap the harness names as poisonous

`qwen3.6-27b-vllm.yaml:20` and `qwen3.8-27b-vllm.yaml:20` both set `max_tokens: 24576`
(verified by grep). Your established fact: that cap sits below the checkpoint's own mean

131072`, not the 57344 the issue comment argued for — the PR's own comment records that even

Note the discrepancy with the brief: the brief attributes the "2 of 12 at level 3" measurement
to the shipped 24576 cap. PR #137's config comment attributes it to 57344. Either reading
condemns 24576 harder, so nothing downstream changes, but the number belongs to the larger cap.

`qwen-vllm.yaml` (#131) is the same checkpoint as `qwen3.6-27b-vllm.yaml` at `temperature:
0.0`. It misleads only if someone runs it; if they do, `report.py:label` gives both columns
the header `Qwen/Qwen3.6-27B` and disambiguates by bracketed sampling. PR #137 deletes it.

### 1.4 #135 — API errors leave the denominator, truncations do not

This is the mechanism the issue does not name, and it is the sharper half of it.

`score_one` writes `score=None` for an API error (`evals/score.py:59-63`), and `_stats`
averages over `ok = [r for r in records if r["score"] is not None]` (`:101-103`). So an item
lost to a timeout is **removed from the cell**, while a truncated item is scored (near zero)
and kept.

Timeouts correlate with generation length, which correlates with level. The August pilot has
the shape: `qwen3.6-27b`'s `api_err` was 0.098 / 0.148 / 0.218 at L03/L06/L09 — rising with
level. So a model that times out on hard items has its per-task mean computed over a
subsample tilted toward the easy items, **and it looks better for it**.

`n_api_error` is per-group in `metrics.json` and in `results.csv`, but the rendered
`report.md` shows it only run-wide in the coverage table (`report.py:128-136`). The per-task
tables print `n_scored` in brackets, which is the tell — but it is the same bracket that
carries the filtered-run case, so it reads as bookkeeping.

PR #144 splits `n_api_error` by cause and adds latency headroom. Merge it before the sweep, or
the level-biased denominator is invisible.

implies.

## 3. Where the benchmark measures something other than what it claims

Every number in this section is computed correctly and the conclusion a reader draws is still
wrong. This is the section I would act on first after the sweep gates.

### 3.1 The ordering axis is an A/A comparison on 11 of 12 tasks (#113)

The report prints a `by_task_ordering` breakdown (`evals/score.py:216`, `report.py`
`write_csv`), and `tasksets/standard.yaml:34-46` justifies shipping all four orderings.

**I disagree with the issue's own headline, and the correction matters.** "It duplicates
`last_link_elitist` on 11 of 12 tasks" reads as "the rows are copies". They are not:

```
$ python3 -c "... compare each lld row's question+reference against its lle sibling ..."
lld rows identical to lle (question+reference): 0   differ: 120
```

The ordering is mixed into the seed, so every `last_link_democratic` row is a different theory.
What duplicates is the **semantics of the label**: `last_link_ordering.py` compares
`argument.last_defeasible_rules`, `any/all` equals `all/any` on a singleton, and #113 measures
zero arguments with more than one last defeasible rule across 2,399 arguments (except 4 of 884
in `status_query`).

So the distortion is not inflated item counts. It is that **a quarter of the grid is labelled
with an axis that carries no information on eleven tasks**, and the report invites the reader
to compare those two columns. A difference between the `last_link_elitist` and
`last_link_democratic` columns at 10 items per cell is noise presented as an ordering effect.
The `weakest_link` half is live and should stay.

### 3.2 `counter_argument_strict` measures grep execution, not preference reasoning (#139, subsuming #93, #94, #99, #116)

#139 is right and it is the best-argued issue in the backlog. The gold is a two-hop walk of the
printed theory; your facts give 1.0 on 40/40 grid and 40/40 off-grid, zero `prefer_*` lines in
32/32 strict references built, and line count == `min_directives` on 32/32. Strict rules are
unattackable by construction (`aspic.py:1214`, following Modgil & Prakken 2014), so the
preference machinery, the elitist/democratic axis, the weakest/last-link axis, the decoy and the
contested premises are all inert on that arm.

Forty rows — 8.3% of the grid — carry a per-task column in `report.md` headed
`counter_argument_strict`, beside eleven columns that measure reasoning. A reader ranking models
on that column is ranking them on mechanical template execution. The pilot shows models do not
saturate it (gemma-4-31b-it at 0.494 against plain 0.075 at L9), which makes it worse, not
better: a live-looking number measuring the wrong thing is harder to discount than a flat one.

#93, #94, #99 and #116 are all facets of this and should be closed by whatever #139 decides.
**My recommendation: option 3, report only `plain - strict`.** It is the only option that moves
no hash, it preserves the ablation (which is the thing of value), and it removes the standalone
column that does the misleading. Cutting the arm loses the only place the benchmark varies one
thing over a fixed theory.

### 3.3 A level is not an ordinal rung, within `defence` (#134) or across modes (#96)

Both reproduce on the shipped artifact, read straight out of the gold:

```
$ python3 -c "... metadata.gold.min_directives by level ..."
defence         {3:{2}, 6:{3}, 9:{3}, 12:{4}, 15:{5}}
attack          {3:{3}, 6:{4}, 9:{5}, 12:{6}, 15:{7}}
attack_defense  {3:{3}, 6:{4}, 9:{4}, 12:{5}, 15:{5}}
```

`defence` L6 and L9 both cost 3, and across that step `base_status` flips `UNDECIDED` ->
`OVERRULED` and `n_strict_attackers` goes 0 -> 1 (your fact). `attack` L6 costs 4, more than
`defence` L9's 3, so "level 9" names two different workloads.

The pilot's `defence` score falling 0.575 -> 0.025 across L06->L09 (your fact) is exactly the
reading this corrupts: it looks like a capability cliff and the generator changed the question's
category at the same point. `by_task_level` in `results.csv` is where a level curve gets drawn,
and there is nothing beside it saying the rungs are not a scale.

The fix that matters before publishing is two sentences in `docs/dataset-card.md`. Not a gate on
the run.

### 3.4 `semantics_query`'s `corrected` column is a ratio of small numbers (#104)

The floor is 0.806 at L3 (`docs/dataset-contract.md:552-555`), so `1 - floor = 0.194`. The grid
gives 8 items per (task, level) cell (480 / 12 tasks / 5 levels) and 40 per task, so:

- one flipped item in a (task, level) cell moves `mean` by 0.125 and `corrected` by
  0.125 / 0.194 = **0.644**;
- one flipped item in the per-task mean moves `corrected` by 0.025 / 0.194 = **0.129**.

The cause is #104's: the balance guard at `semantics_query.py:458` counts statuses pooled across
semantics, so `MAX_STATUS_SHARE` holds the marginal at 0.445 while `credulous preferred` sits at
0.838. A per-semantics constant scores 0.671 reading no theory.

Nothing here is computed wrongly — the floor is measured, `corrected` is `(mean - floor) /
(1 - floor)` as documented. The conclusion goes wrong because the `corrected` column puts
`semantics_query` on the same visual scale as tasks whose floor is 0.000, where the same
one-item flip moves `corrected` by 0.025. **#104's option 3 is free and should be taken for this
sweep:** report `semantics_query` without `corrected`, or with a note that its amplification
factor is 5.2x.

### 3.5 Six items... eight items... per cell either way, it is not a level curve (#132)

**A correction to the brief.** "`take: 2` gives 6 items per (task, level) cell" is the
post-#113 number, and #113 has not landed. On `main` today it is **8** (4 orderings x 2 seeds),
so a cell mean moves in steps of 0.125, not 0.167. `#132`'s table says so itself ("after
dropping `last_link_democratic`"); the brief dropped the condition.

Either way the conclusion holds and is the same one: at 8 items with near-binary construction
scores, an adjacent-level difference is one flipped item. Model ranking per task (40 items) and
the recognise-versus-construct contrast (240 construction items pooled, 6 tasks x 40) survive.
Level curves do not. If the sweep is meant to answer a level-curve question, `take` has to go to
10 before the freeze, not after.

## 4. What must land before a sweep is worth running

Ordered. Steps 1-5 all have to be settled before the single regeneration, because each moves
`taskset_hash` or `PROMPT_VERSION`.

1. **Decide PR #151.** Nobody has flagged this and it is the biggest open question. It is not a
   model-config PR: it rewrites `AnswerTemplate.instruction` to demand
   `<thought>...</thought>` (a prompting technique inside the dataset layer, against the split you
   recorded), adds AND-notation to `formalization_notation()`, rewrites
   `defeat_diagnosis._render_prompt` with field-interpretation help, replaces
   `formalization.score_value`'s structural key with an alpha-equivalence walk, and bumps
   `PROMPT_VERSION` to 8 and `SCORING_VERSION` to 5 — colliding with PR #149's bump to 8.
   Split the model configs out, or close it. Everything below is downstream.
   *Nobody has written this.*
2. **Set one token-budget policy across the whole roster**, then merge **PR #137**. The per-model
   caps in #151 (8192 -> 65536) make the columns incomparable by construction; #137 alone fixes
   only the two Qwen files. Whatever policy you pick, record it where the report can print it.
   *#137 is written; the roster-wide policy is not.*
3. **Fix #138 and #141 together.** Nine lines apart in `semantics_query.py`; #138 moves gold on
   four rows and #141 moves metadata on forty. *Nobody has written either.*
4. **Decide #113, #132 and #139.** Grid shape and row count. #113 and #132 change how many rows
   exist; #139's cheapest option (paired difference only) changes no rows and is a reporting
   change. *All three are decisions; no code exists.*
5. **Merge PR #149** once the number in step 1 is settled, so `PROMPT_VERSION` moves with the
   question set. *Written.*
6. **Re-freeze `data/taskset.jsonl`.** This is the step that actually matters: it is what brings
   the v6/v7 prompt rules to the models (1.1), removes #124's row (1.6), and makes the shipped
   artifact describe `main`. Budget ~10 minutes (#111's measurement: 9 min 34 s, 61% of it one
   cell). *Nobody has done this; it is blocked on 1-5.*
7. **Merge PR #144** before launching, so the API-error denominator (1.4) is visible while the
   run is happening rather than after. *Written.*
8. **Run #130's presence-penalty probe** — one model, one level, two `run_id`s, compare
   `truncated_rate` against `zero_with_region`. The pilot lost three of seven models to
   repetition loops at Qwen's own recommended sampling; without this the sweep can lose them
   again and the cost is a wasted sweep, not a wrong number. *Nobody has run it.*
9. **Merge PRs #140, #143, #146, #147, #150, #153** whenever convenient. None of them changes a
   shipped number; #143 and #147 add test coverage that would have caught two of the defects
   above, which is worth having before the next round rather than after. *All written.*
